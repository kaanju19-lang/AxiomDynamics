# D09 — Data Processing & Security Addendum (DPA)

**Docket position:** D09. The security and data protection addendum. Standalone because the Railroad's IT security review runs on a different timeline from procurement.

> **Drafting status:** Commercial grade. Requires review by the Railroad's CISO and legal counsel. Designed to satisfy a Class I carrier's vendor security assessment.

---

## 1. Scope and applicability

This Data Processing & Security Addendum ("DPA") applies to any lawful processing of Railroad Data by AxiomDynamics ("Supplier"). It is incorporated into D07 (Master Contract) and all orders.

**Where this DPA conflicts with D07 or any order, this DPA governs on matters of data protection and security.** On all other matters, D07 governs.

---

## 2. Definitions

**Railroad Data** — any data owned by the Railroad, including detector data, advisory records, disposition records, maintenance history, and operational logs.

**Personal Data** — data relating to an identified or identifiable natural person (e.g., reviewer names, employee IDs, training records). Personal data is a subset of Railroad Data.

**Processing** — any operation on Railroad Data, including collection, storage, use, alteration, deletion, or transfer.

**Security Incident** — a confirmed breach or suspected breach of security leading to accidental or unlawful destruction, loss, alteration, unauthorized disclosure of, or access to Railroad Data.

**Subprocessor** — any third party engaged by Supplier to process Railroad Data on its behalf.

---

## 3. Data residency and the air-gap guarantee

### 3.1 Where data lives

Under AD-1 (B01), the Platform is **fully on-premise**. Railroad Data is stored on the Railroad's own infrastructure (the server or container where the Platform runs). It does not leave the Railroad's network.

**Supplier has no access to Railroad Data in normal operation.** Supplier does not receive, store, process, or transmit Railroad Data to any cloud service, analytics platform, backup location, or third party.

### 3.2 No outbound network

The Platform contains no mechanism to:
- Send data to Supplier or any external service.
- Contact a licence server or phone-home.
- Report telemetry, usage, or errors.
- Download updates (updates are delivered out-of-band via secure transfer and applied by the Railroad).

See B05 (Data Flow & Residency) for the code-verified confirmation.

### 3.3 Data boundary

All Railroad Data resides:
- On the Railroad's server (physical or virtual) where the Platform is installed.
- On backup media created and managed by the Railroad.
- On archived exports or reports generated by the Railroad.

None of these locations involve Supplier systems.

### 3.4 Support access

If the Railroad requests Supplier assistance with diagnosis:
- Supplier performs a **read-only, time-limited session** to the affected component.
- The Railroad controls access (network connectivity, credentials, session duration).
- No data is copied to Supplier systems; diagnostics are performed in place.
- A record of the session is logged (by the Railroad and by Supplier) and retained for 90 days.

**On-site or remote access requires:**
- Prior written authorization from the Railroad's IT Director.
- A defined scope and duration.
- A support engineer bound by D11 and D09 confidentiality.
- Non-disclosure of what was observed to any other customer.

## 4. Security controls

### 4.1 Organizational controls

**Supplier maintains:**
- A documented security policy covering access control, incident response, backup, and acceptable use.
- Annual security training for all personnel with access to Supplier's systems (not Railroad Data, which Supplier doesn't hold).
- Background verification for personnel with access to Supplier IP and Platform source code (D07 §7.7).

**Personnel do not have access to Railroad operations or data.** No Supplier employee sits embedded at the Railroad, no engineer has standing credentials to Railroad systems, and no one has access "just in case."

### 4.2 Technical controls (in the Platform)

| Control | Implementation | Status |
|---|---|---|
| **Encryption at rest** | SQLite database can be encrypted using sqlcipher or filesystem encryption (Railroad's choice). | Configurable by Railroad |
| **Encryption in transit** | API is HTTP-only within the local network. **If the Railroad requires HTTPS, they implement a reverse proxy (nginx, Apache) in front of the Platform.** The Platform itself does not terminate TLS. | Railroad responsibility |
| **Authentication** | The Platform currently uses local user accounts with passwords. **AD-2 (B01) recommends signed certification registry with issued credentials.** This is a gap; see §4.4. | Partial — authentication is local, not cryptographically registered |
| **Authorization** | Role-based access (Operator, Reviewer, Administrator) per C02. Enforced by the Platform. | Implemented per role model |
| **Audit logging** | All disposition writes, user login/logout, configuration changes, and patch applications are logged to an append-only table. Logs cannot be modified or deleted (only exportable by an Admin). | Implemented (AD-3) |
| **Data validation** | Input validation on disposition fields (reviewer name, cert ID, disposition text). Malformed data is rejected. | Implemented; schema incomplete (see B01 §7 gap register) |
| **Backup** | The Railroad performs nightly backups of the SQLite database (daily full, hourly WAL). Supplier does not hold backups. | Railroad responsibility |
| **Time synchronization** | The Platform relies on the host's system time. The Railroad must configure NTP for accurate timestamps in the disposition ledger. | Railroad responsibility |

### 4.3 Operational controls

**Supplier commits to:**
- **No unauthorized access:** Supplier personnel access the Platform only with explicit Railroad authorization and per §3.4.
- **Vulnerability management:** Supplier scans dependencies for known vulnerabilities before each release and notifies the Railroad of security patches per D06 §3.2.
- **Secure development:** Code review before merge; no committing secrets (API keys, credentials) to the repository.
- **SBOM:** Supplier provides a Software Bill of Materials (SBOM) with each release (B04 §7 gap is being closed).
- **Supply chain:** Supplier verifies the integrity of dependencies (SHA-256 hashes) and documents the source of each component.

### 4.4 Known gaps and remediation roadmap

The following controls are **not yet implemented** but are on the remediation roadmap:

| Gap | Impact | Remediation | Target |
|---|---|---|---|
| **Authentication is local, not cryptographically registered** | A malicious insider with database access could potentially forge a disposition record. | Implement signed certification registry (AD-2 per B01 §7) | Q2 2027 |
| **No SBOM artifact in releases** | The Railroad cannot independently verify the dependency chain. | Generate SBOM (SPDX or CycloneDX) per release | Q1 2027 |
| **No hash verification of dependency downloads** | A compromised PyPI could serve malware as a dependency. | Require SHA-256 pinning of all dependencies in requirements.txt | Q1 2027 |
| **No signed release artifacts** | A malicious actor could replace a release archive with a trojan. | Sign releases with GPG; provide public key | Q2 2027 |

**These gaps are disclosed proactively.** The Railroad should assess whether they are acceptable for its risk tolerance. If not, the Railroad may delay production deployment until the remediation is complete (escrow of current version per D13 remains available).

## 5. Data retention and deletion

### 5.1 Retention period

**Default:** Railroad Data is retained indefinitely in the Platform database, subject to the Railroad's retention policy.

**Railroad can configure retention:** AxiomDynamics recommends retaining disposition records for a minimum of three (3) years (to support audit, incident investigation, and regulatory inquiry). Detector data may be purged more aggressively (e.g., after 180 days) if the Railroad wishes to reduce database size.

### 5.2 Data deletion

The Railroad may delete Railroad Data at any time by:
- Purging records from the Platform (via an admin interface or SQL).
- Destroying the database file (this deletes all records).
- Purging backup media.

**Upon termination (D07 §15.5), the Railroad exports its data and then destroys the database.** Supplier certifies destruction in writing within **thirty (30) days of termination**.

### 5.3 Supplier-side deletion

Since Supplier holds no Railroad Data in normal operation, no Supplier-side deletion is required. If support sessions have copied diagnostic data to Supplier systems (which is prohibited per §3.4), Supplier deletes it within **five (5) business days** of the session ending.

## 6. Security incident notification

### 6.1 Notification obligation

If Supplier becomes aware of a security incident affecting the Platform, Supplier notifies the Railroad **without undue delay and in any event within seventy-two (72) hours** of confirmation, providing:
- Description of the incident and what was affected.
- Estimated number of records or systems involved.
- Containment measures taken.
- Root cause (if known).
- Measures to prevent recurrence.

### 6.2 What constitutes a reportable incident

Under §6.1, the following are reportable:
- Unauthorized access to the Platform or Railroad Data (including attempted access that succeeded partially).
- Loss or theft of a device containing Platform data or credentials.
- Malicious code introduced into the Platform or dependency chain.
- Vulnerability disclosed by a third party (e.g., a security researcher) that affects the Platform in production.
- Breach of Supplier's own systems that could expose Railroad Data (even if no Railroad Data was actually accessed).

**The following are NOT reportable** (no notification required):
- Routine failed login attempts.
- Scheduled maintenance or patches.
- Vulnerability disclosures that are not yet weaponized and for which no patch exists (the Railroad is notified when a patch becomes available, per D06 §3.2).

### 6.3 Railroad notification to Supplier

If the Railroad discovers a vulnerability or incident in the Platform, it notifies Supplier within **twenty-four (24) hours** so that Supplier can investigate and patch.

### 6.4 Post-incident review

Within **thirty (30) days** of containment, Supplier provides a written root-cause analysis and remediation plan. The parties schedule a joint review within **ten (10) business days** of the report.

### 6.5 Regulatory notification

If the incident is reportable under applicable law (e.g., data breach notification laws), the Railroad is responsible for notifying regulators and affected individuals. Supplier assists by providing relevant information but does not make regulatory notifications on behalf of the Railroad.

## 7. Subprocessors and third-party dependencies

### 7.1 Subprocessors

**Supplier uses no subprocessors to process Railroad Data.** Under AD-1, there is no cloud hosting, no analytics vendor, no outsourcing of data processing.

**If a subprocessor is added in future:**
- Supplier notifies the Railroad at least **thirty (30) days** in advance.
- The subprocessor is bound by confidentiality and security obligations no less stringent than this DPA.
- The Railroad may object within thirty days; if the objection is not resolved, the Railroad may terminate the affected order without penalty.

### 7.2 Third-party components (SBOM)

Supplier provides a Software Bill of Materials (SBOM) with each release, listing all third-party libraries (name, version, license, source URL) per B04. Any change to the SBOM (new dependency, version bump, addition or removal) is disclosed in the release notes.

The Railroad may audit the SBOM and request clarification on any component.

## 8. Access control and personnel management

### 8.1 Credentials

**Railroad personnel** manage their own credentials (passwords, API keys for any integrations). The Platform does not issue credentials to Supplier personnel.

**Supplier personnel** who require access to the Platform for diagnostic support (per §3.4) receive temporary, time-limited credentials issued by the Railroad, revoked at the end of the session.

### 8.2 Termination of access

When a Railroad employee leaves or changes roles, the Railroad revokes their Platform access. Supplier is not involved in this process.

The Railroad notifies Supplier of any Certified Reviewer whose certification is revoked or whose employment terminates, so that the certification registry is updated (C02 §4.2).

### 8.3 Password policy

The Platform enforces a minimum password length and complexity (configurable by the Railroad). The Railroad is responsible for its own password policies, rotation, and account management.

---

## 9. Confidentiality and non-disclosure

All Railroad Data and any information observed during support sessions is confidential per D11 (Mutual NDA). Supplier does not use Railroad Data for model training, benchmarking, or any purpose other than support.

**Aggregated learning:** Supplier may use anonymized, aggregated data (e.g., "across all deployments, bearing failures typically occur at X temperature range") to improve the Platform, **provided such data cannot be traced back to the Railroad** and does not reveal its competitive position or operational details. See D13 §2.

---

## 10. Audit rights

### 10.1 Security audit

Once per year, the Railroad may audit Supplier's compliance with this DPA. Audit scope is limited to:
- Supplier's security policy and training records.
- Incident response procedures and logs.
- Subprocessor list (currently none).
- SBOM and dependency management for the past 12 months.

Audit is conducted by the Railroad or a third party bound by confidentiality. Supplier provides documentation and, if requested, interviews with security personnel.

### 10.2 SBOM verification

The Railroad may independently verify the SBOM against the actual dependencies installed in the Platform. If discrepancies are found, Supplier investigates and remediates within thirty days.

---

## 11. Data protection impact assessment (DPIA)

If the Railroad is required by law or policy to conduct a DPIA, Supplier provides:
- A description of the processing (what data, for what purpose, how it is used).
- The security measures in §4.
- Any risks to personal data and how they are mitigated.

Supplier cooperates with the Railroad's DPIA process but does not conduct the DPIA independently.

---

## 12. Compliance with law

Both parties comply with applicable data protection law, including (where applicable):
- **United States:** state privacy laws (CCPA/CPRA, etc.) and federal regulations.
- **Canada:** PIPEDA and provincial privacy laws.
- **Mexico:** Federal Law on Protection of Personal Data Held by Private Parties (if applicable).

Supplier does not transfer Railroad Data outside the Railroad's jurisdiction without explicit written consent.

## 14. Term and survival

This DPA applies during the term of the licence and for **two (2) years after termination** (to cover audit, investigation, and data retention obligations).
