# D09 — Data Processing & Security Addendum (DPA)

**Docket position:** D09. The security and data protection addendum. Standalone because the Railroad's IT security review runs on a different timeline from procurement.

> **Drafting status:** Commercial grade. Requires review by the Railroad's CISO and legal counsel. Designed to satisfy a Class I carrier's vendor security assessment.

---

## 1. Scope and applicability

This Data Processing & Security Addendum ("DPA") applies to any lawful processing of Railroad Data by AxiomDynamics ("Supplier"). It is incorporated into D07 (Master Contract) and all orders.

**Where this DPA conflicts with D07 or any order, this DPA governs on matters of data protection and security.** On all other matters, D07 governs.

---

## 2. Definitions

**Railroad Data** — any data owned by the Railroad, including detector data, advisory records, disposition records, maintenance history, and operational logs.

**Personal Data** — data relating to an identified or identifiable natural person (e.g., reviewer names, employee IDs, training records). Personal data is a subset of Railroad Data.

**Processing** — any operation on Railroad Data, including collection, storage, use, alteration, deletion, or transfer.

**Security Incident** — a confirmed breach or suspected breach of security leading to accidental or unlawful destruction, loss, alteration, unauthorized disclosure of, or access to Railroad Data.

**Subprocessor** — any third party engaged by Supplier to process Railroad Data on its behalf.

---

## 3. Data residency and the air-gap guarantee

### 3.1 Where data lives

Under AD-1 (B01), the Platform is **fully on-premise**. Railroad Data is stored on the Railroad's own infrastructure (the server or container where the Platform runs). It does not leave the Railroad's network.

**Supplier has no access to Railroad Data in normal operation.** Supplier does not receive, store, process, or transmit Railroad Data to any cloud service, analytics platform, backup location, or third party.

### 3.2 No outbound network

The Platform contains no mechanism to:
- Send data to Supplier or any external service.
- Contact a licence server or phone-home.
- Report telemetry, usage, or errors.
- Download updates (updates are delivered out-of-band via secure transfer and applied by the Railroad).

See B05 (Data Flow & Residency) for the code-verified confirmation.

### 3.3 Data boundary

All Railroad Data resides:
- On the Railroad's server (physical or virtual) where the Platform is installed.
- On backup media created and managed by the Railroad.
- On archived exports or reports generated by the Railroad.

None of these locations involve Supplier systems.

### 3.4 Support access

If the Railroad requests Supplier assistance with diagnosis:
- Supplier performs a **read-only, time-limited session** to the affected component.
- The Railroad controls access (network connectivity, credentials, session duration).
- No data is copied to Supplier systems; diagnostics are performed in place.
- A record of the session is logged (by the Railroad and by Supplier) and retained for 90 days.

**On-site or remote access requires:**
- Prior written authorization from the Railroad's IT Director.
- A defined scope and duration.
- A support engineer bound by D11 and D09 confidentiality.
- Non-disclosure of what was observed to any other customer.

## 4. Security controls

### 4.1 Organizational controls

**Supplier maintains:**
- A documented security policy covering access control, incident response, backup, and acceptable use.
- Annual security training for all personnel with access to Supplier's systems (not Railroad Data, which Supplier doesn't hold).
- Background verification for personnel with access to Supplier IP and Platform source code (D07 §7.7).

**Personnel do not have access to Railroad operations or data.** No Supplier employee sits embedded at the Railroad, no engineer has standing credentials to Railroad systems, and no one has access "just in case."

### 4.3 Operational controls

**Supplier commits to:**
- **No unauthorized access:** Supplier personnel access the Platform only with explicit Railroad authorization and per §3.4.
- **Vulnerability management:** Supplier scans dependencies for known vulnerabilities before each release and notifies the Railroad of security patches per D06 §3.2.
- **Secure development:** Code review before merge; no committing secrets (API keys, credentials) to the repository.
- **SBOM:** Supplier's generator is **built (2026-11-11)**; **no released artefact has yet carried an SBOM.** See §7.2 and D10 Part 5 for the distinction between a tool that exists and a document a customer holds.
- **Supply chain:** Supplier documents the source of each component in **D10**, which since 2026-11-11 also lists the seven libraries bundled inside the numpy wheel rather than only the package name. **Hash pinning is built (2026-11-11) and the release path now enforces it; `requirements.txt` is not yet pinned**, because the pin must be observed on a host with index access. **Release signing is built (2026-11-11); no key is issued yet.** See §4.4, §7.2, §7.3.

> **Why this section was corrected.** It previously stated as present commitments that an SBOM is provided with each release and that dependency integrity is verified by SHA-256. **Both were untrue, and both were listed as gaps six lines further down in §4.4.** A security schedule that lists a control as committed in §4.3 and unimplemented in §4.4 is worse than one that admits the gap once: it tells the reviewer what they want to hear and then contradicts itself, which is exactly the pattern that destroys a vendor's credibility in a CISO review.

The following controls are **not yet implemented** but are on the remediation roadmap:

| Gap | Impact | Remediation | Target |

| **The ledger export signature cannot name the signer** | **Split 2026-11-11 — the disposition half is closed, the export half is not.** The export bundle has been signed (HMAC-SHA256) and independently verifiable since 2026-11-09, and detects altered, added, reordered and removed records, a ledger that has shrunk since a bundle you already hold, and rows deleted from the front of the ledger. **What changed on 2026-11-11: a disposition row can now be bound to a registered reviewer and the binding verified by a recipient.** `backend/attribution.py` holds an append-only, **hash-chained** certification registry — not signed: it is tamper-evident to a re-computing reader, which is a weaker property than authentication and is stated as such in the module docstring — with `BEFORE UPDATE`/`BEFORE DELETE`/`INSERT OR REPLACE` refused, and each attestation is an HMAC over the row's own `record_hash` under that reviewer's 32-byte key, travelling inside the exported record. A recipient holding the reviewer key **and the name bound to it** recomputes it; one without the key still checks that the attestation names the reviewer and certificate the row names, that the key was registered before the attestation, and that the row was not recorded after the key was revoked. **What this does not close:** the *export* signature is still symmetric and unnamed — attribution is per-disposition, not per-bundle — the claim is about a key holder, not a human being at a keyboard (binding a key to a person is credential issuance under §4.5), the scheme is HMAC so a holder of reviewer A's key can attest as A, and it cannot prove **when** anything happened because no external timestamping exists on an air-gapped box. A certificate revoked mid-session stops writing immediately. **What remains:** entry requires a live *session*, not an *attestation* — a row without an attestation is still an honest state the manifest counts rather than an error — and key custody and joiner/mover/leaver are a written procedure, not code. | Bind export keys to certified identities under AD-2; require attestation as well as a session at entry; key custody and joiner/mover/leaver procedure; signed key directory; move to an asymmetric signature with a published public key when a vetted library is available | Q2 2027 |
| **No automatic off-box replication of the ledger** | **Partly closed 2026-11-10.** The §4.5.4 series is now produced on its cadence by `backend/ledger_replication.py` — monthly full, weekly incremental, each chained to the last, zero-record weeks kept, nothing overwritten — and `inspect` verifies every bundle against its predecessor and reports a missing period. What remains open is the **carriage**: the series is written to a directory on the Platform host and nothing moves it further, deliberately, because §3.2 promises the Platform has no outbound network. Moving the series to backup media is the Railroad's step under §3.3, and until it is done a lost disk still loses the ledger. A party with write access to the database file can still drop the triggers and recompute the chain between exports; only a recipient who **keeps each bundle as it arrives** detects that, which is why the custody procedure remains a control and not an administrative detail. | Off-box carriage of the produced series, with receipt acknowledgement; see B01 §4.5a and §7 items 11–12 | Q2 2027 |
| **No SBOM artifact in releases** | **Built 2026-11-11, not yet in a shipped release.** The Railroad cannot independently verify the dependency chain from a released artefact. `tools/sbom.py` generates a CycloneDX 1.5 document from the *installed* tree — component, exact version, a SHA-256 over every installed file, and the native libraries bundled inside the numpy wheel — and `verify` recomputes the digest on the Railroad's machine. ### 4.5 Ledger export key custody and export procedure

Three gaps in §4.4 are controlled by procedure rather than by cryptography, and a procedure that is not written down is not a control. This is the procedure.

**4.5.1 The key.** The export signing key is 32 raw bytes from the operating system's CSPRNG, generated on the platform host with `python3 -m backend.ledger_export keygen --key-file <path>`. It is written mode `0600`, is excluded from version control by `.gitignore`, and is held in two copies: one in the Railroad's sealed physical storage, one with AxiomDynamics in escrow. It is **never** transmitted by email, chat, ticket or any other channel that leaves a copy. A key file that has been committed to a repository, pasted into a message, or stored beside a bundle it signed is treated as compromised and rotated.

**4.5.2 The key_id.** Every key has a `key_id`, the first 16 hex characters of its SHA-256, printed at generation and published. It is safe to share and lets a recipient distinguish "wrong key" from "forged bundle" — a distinction that saves an investigation.

**4.5.3 Rotation.** Rotating the key makes every bundle signed under the previous key unverifiable against the new one, so rotation is recorded in a custody log with the `key_id` it retired, the date, the reason, and the `key_id` of its successor. The old key is retained, not destroyed, for as long as any bundle it signed is retained. Key compromise is a reportable incident (§6.2), not an administrative correction.

**4.5.4 The export schedule.** A signed, full export is produced **monthly** and an incremental export (`--after-id`, with `--previous-export-hash` naming the last bundle) **weekly**. The Platform produces this series itself on that cadence — `backend/ledger_replication.py run`, invoked by the Railroad's scheduler — writing each bundle beside the previous one with nothing overwritten, and `backend/ledger_replication.py inspect` verifies the series and reports any missing period. **Producing the series is not the same as removing it from the box.** Because §3.2 promises no outbound network, the Platform does not transmit a bundle anywhere; carrying the series to backup media is a step the Railroad performs under §3.3, and until it does, a lost disk still loses the ledger.

The Railroad retains each bundle as received, in order, without overwriting one with a later one — this is the single control that detects a ledger truncated or rewritten between exports, and discarding old bundles forfeits it. A week with no new dispositions produces a valid **zero-record** bundle; that is expected and must be kept, because a gap in the sequence is indistinguishable from a removed bundle. Quarterly, the Railroad verifies the series with `backend/ledger_replication.py inspect --key-file <key>` on the platform host, and verifies one retained bundle independently with `tools/verify_ledger_export.py` on a machine with no connection to the platform host, recording both results.

> **Why the sequence matters more than any single bundle.** A single bundle proves its own content is intact. It cannot prove the ledger was not wiped before it was made — an attacker who deletes every row produces an empty ledger, the exporter truthfully signs an empty bundle, and it verifies clean. What catches that is this bundle failing to extend the last one you hold. **A series kept from commissioning is the evidence; one bundle is a snapshot that cannot testify about its own past.**

**4.5.5 What the receipt establishes.** Receipt of a verified bundle establishes that the ledger content at export time matched what was signed, that it extended every bundle previously received, that the ledger has not shrunk since, and — for any record carrying an `attribution` block — that the reviewer and certificate named in that block are the ones the row itself names, and that the attestation was made by a key registered and not yet revoked at the time. If the reviewer's key is held, receipt also establishes that the attestation recomputes. **The reviewer key must be supplied together with the name of the reviewer it belongs to** — a key alone proves that some key holder produced the attestation, and the block's own name label is not covered by the cryptographic value; the verifier therefore checks the label against the name you supplied and reports a failure if they disagree. A recipient holding no reviewer key can check the block's internal consistency and its ordering against the registry times, but **cannot distinguish an honest attestation from a fabricated one**, because the scheme is symmetric. **Since 2026-11-11 the recipient need not be told the name at all.** The signed **reviewer key directory** (`backend/key_directory.py`, built by `tools/publish_key_directory.py`, verified on a recipient machine by `tools/verify_key_directory.py`) publishes the reviewer↔key_id↔cert_id bindings and their revocation times, signed with the same export key as the bundles. A recipient verifies the directory once and takes every `key_id -> reviewer` binding from it, so the name that used to be typed on the command line is now read from a signed document. It carries **no key material** — a key_id is a truncated digest — and the directory's own signature is symmetric, so it establishes that the export-key holder authored those bindings, not that they were entitled to. That is portable and tamper-evident rather than authenticated, and it does not substitute for the asymmetric signature B01 §7 item 11 still calls for. It does not establish the identity of the **export** signer, the time of signing, that a key holder was a particular human being, or that the ledger was intact before the first bundle in the series — those remain the AD-2 dependency in §4.4 and the custody discipline above — and it must not be represented as more.

**4.5.6 If a bundle fails verification.** Stop, preserve the bundle unmodified, verify against the correct `key_id` first, and only if it still fails treat it under §6 as a reportable integrity incident. Do not re-export over it.

## 5. Data retention and deletion

### 5.1 Retention period

**Default:** Railroad Data is retained indefinitely in the Platform database, subject to the Railroad's retention policy.

**Railroad can configure retention:** AxiomDynamics recommends retaining disposition records for a minimum of three (3) years (to support audit, incident investigation, and regulatory inquiry). Detector data may be purged more aggressively (e.g., after 180 days) if the Railroad wishes to reduce database size.

### 5.2 Data deletion

The Railroad may delete Railroad Data at any time by:
- Purging records from the Platform (via an admin interface or SQL).
- Destroying the database file (this deletes all records).
- Purging backup media.

**Upon termination (D07 §15.5), the Railroad exports its data and then destroys the database.** Supplier certifies destruction in writing within **thirty (30) days of termination**.

### 5.3 Supplier-side deletion

Since Supplier holds no Railroad Data in normal operation, no Supplier-side deletion is required. If support sessions have copied diagnostic data to Supplier systems (which is prohibited per §3.4), Supplier deletes it within **five (5) business days** of the session ending.

**Retained export bundles are not Railroad Data in play here.** Replacement media or the platform host itself may leave service; the §4.5 bundles the Railroad has retained do not need to be deleted on replacement and should not be, because they are the reference against which future exports are checked.

## 6. Security incident notification

### 6.1 Notification obligation

If Supplier becomes aware of a security incident affecting the Platform, Supplier notifies the Railroad **without undue delay and in any event within seventy-two (72) hours** of confirmation, providing:
- Description of the incident and what was affected.
- Estimated number of records or systems involved.
- Containment measures taken.
- Root cause (if known).
- Measures to prevent recurrence.

### 6.2 What constitutes a reportable incident

Under §6.1, the following are reportable:
- Unauthorized access to the Platform or Railroad Data (including attempted access that succeeded partially).
- Loss or theft of a device containing Platform data or credentials.
- **Compromise, suspected compromise or loss of an export signing key, or a bundle that fails verification with the correct `key_id` (§4.5).** Either event means the integrity evidence for the disposition ledger can no longer be relied on until the cause is established.
- Malicious code introduced into the Platform or dependency chain.
- Vulnerability disclosed by a third party (e.g., a security researcher) that affects the Platform in production.
- Breach of Supplier's own systems that could expose Railroad Data (even if no Railroad Data was actually accessed).

**The following are NOT reportable** (no notification required):
- Routine failed login attempts.
- Scheduled maintenance or patches.
- Vulnerability disclosures that are not yet weaponized and for which no patch exists (the Railroad is notified when a patch becomes available, per D06 §3.2).

### 6.3 Railroad notification to Supplier

If the Railroad discovers a vulnerability or incident in the Platform, it notifies Supplier within **twenty-four (24) hours** so that Supplier can investigate and patch.

### 6.4 Post-incident review

Within **thirty (30) days** of containment, Supplier provides a written root-cause analysis and remediation plan. The parties schedule a joint review within **ten (10) business days** of the report.

### 6.5 Regulatory notification

If the incident is reportable under applicable law (e.g., data breach notification laws), the Railroad is responsible for notifying regulators and affected individuals. Supplier assists by providing relevant information but does not make regulatory notifications on behalf of the Railroad.

## 7. Subprocessors and third-party dependencies

### 7.1 Subprocessors

**Supplier uses no subprocessors to process Railroad Data.** Under AD-1, there is no cloud hosting, no analytics vendor, no outsourcing of data processing.

**If a subprocessor is added in future:**
- Supplier notifies the Railroad at least **thirty (30) days** in advance.
- The subprocessor is bound by confidentiality and security obligations no less stringent than this DPA.
- The Railroad may object within thirty days; if the objection is not resolved, the Railroad may terminate the affected order without penalty.

### 7.2 Third-party components (SBOM)

**Supplier's SBOM generator is built (2026-11-11); no released artefact has yet carried an SBOM.**

`tools/sbom.py` produces a CycloneDX 1.5 document from the **installed** tree, not from `requirements.txt`: each component carries its exact version, a SHA-256 over every file it installed, and the native libraries bundled inside its wheel. A second subcommand, `verify`, recomputes those digests on the Railroad's machine and fails on a substituted wheel, a changed version, a component declared but absent, and a component installed but undeclared. The verification tool imports nothing outside the Python standard library, for the same reason the ledger verifier does.

**What is not yet true, stated plainly.** No release has shipped with an SBOM attached, because no release has shipped since the generator existed. The generator must be run on the **target architecture** — the numpy wheel is platform-specific and an SBOM taken from a build host describes a different set of binaries — and the resulting file must travel with the signed archive. Until that has happened once, the answer to "can we verify your dependency chain from what you gave us" is still no.

**D10 remains the artefact the Railroad can rely on today**, and since 2026-11-11 it lists the seven libraries bundled inside the numpy wheel rather than only the package name. It was previously described here as listing "every third-party component"; it listed one distribution and called it complete, which was wrong. D10 Part 2 now says so.

> **Why this is written as a partly-negative.** This section has been wrong once already: it said Supplier "provides an SBOM with each release" while §4.4 denied it. The rule that came out of that — a control promised in one section and denied in another will be tested by the first auditor who reads both — is why the state above is split into *built* and *shipped* rather than collapsed into "implemented". A generator that exists is not an SBOM a customer holds.

### 7.3 Release artefacts and signing

**Supplier's release-signing tool is built (2026-11-11); no key is issued and no release has been signed.** The ledger export is signed (§4.5); releases are not yet, and the two are not interchangeable.

Every **software** artefact the Railroad has received to date is unsigned — this section is about releases, not data. (The disposition-ledger export *is* signed, since 2026-11-09; see §4.5. It is a data bundle produced on the Railroad's own host, not a release from Supplier, and the two signing stories are deliberately separate.)

`tools/sign_release.py` builds a **reproducible** archive — gzip header mtime pinned, uid/gid normalised, a single fixed mtime across entries, so two builds of identical content produce identical bytes and the signature covers the code rather than the build machine's clock — writes the `MANIFEST.sha256` C01 Part C2 already describes, and signs it with a detached GPG signature verifiable against a supplied public key rather than a local trustdb.

**Why GPG and why it is a different mechanism from the ledger export.** The export signs *data* on the Railroad's host with a symmetric key, so any verifier can also forge; its threat is a Railroad insider changing a disposition. A release signs a *build we ship* with an asymmetric key, so a verifier can check authorship without being able to produce it; its threat is anybody between us and the Railroad substituting a tarball. Asking the Railroad's security team to learn a bespoke scheme would be the same mistake at a different layer, so the tool wraps `gpg` and they check it with the command they already use.

**Until a key is issued and its public half reaches the Railroad by a route they trust**, a software artefact's integrity still rests on the transfer channel and on the Railroad's own verification:

- **Repository checkout.** Where the Railroad clones the source repository, git's own object hashing provides integrity for the tree it receives, against the branch it received it from. That is a check on corruption and on the transported content. **It is not a signature** — it does not prove which key produced a release, and it does not survive a compromised repository host.
- **Sealed-archive transfer (C01 Part B).** Supplier provides a **SHA-256 manifest** of the transferred set, which the Railroad verifies against the files it receives. This detects corruption and in-transit substitution **when the manifest itself is trusted** — and until it is signed, it arrives over the same channel as the archive, which is the weakness. A manifest delivered alongside the thing it describes protects against accident, not against an adversary who can alter both. Since 2026-11-11 the manifest can be signed; the signing becomes meaningful when the public key reaches the Railroad by a path independent of the archive.

**What a release signature will and will not prove, once issued.** It proves the artefact was signed by the private key and has not changed since. It does **not** prove the key was Supplier's unless the public key arrived by a route the Railroad trusts, and it does not prove the build is free of a defect — only that it is the build we signed. Key custody and publication procedure are the control that carries that weight, exactly as with the export key under §4.5.

> **Why this section exists at all.** Signed release artefacts previously appeared exactly once in this document — as a row in the §4.4 gap table. A control disclosed only in a remediation table is not disclosed; it is noted. A CISO reading §7 for the supply-chain position would have found the SBOM gap stated plainly at §7.2 and no corresponding statement about signing, and would reasonably have concluded that if the drafter had addressed one and not the other, the unaddressed one was probably fine. **The rule for this document is that every control in §4.4's gap table has a corresponding statement in the section a reader would look in** — and, since 2026-11-11, that the statement distinguishes a tool that exists from a control that has been applied.

## 8. Access control and personnel management

### 8.1 Credentials

**Railroad personnel** manage their own credentials (passwords, API keys for any integrations). The Platform does not issue credentials to Supplier personnel.

**Supplier personnel** who require access to the Platform for diagnostic support (per §3.4) receive temporary, time-limited credentials issued by the Railroad, revoked at the end of the session.

### 8.2 Termination of access

When a Railroad employee leaves or changes roles, the Railroad revokes their Platform access. Supplier is not involved in this process.

The Railroad notifies Supplier of any Certified Reviewer whose certification is revoked or whose employment terminates, so that the certification registry is updated (C02 §4.2).

### 8.3 Password policy

The Platform enforces a minimum password length and complexity (configurable by the Railroad). The Railroad is responsible for its own password policies, rotation, and account management.

## 9. Confidentiality and non-disclosure

All Railroad Data and any information observed during support sessions is confidential per D11 (Mutual NDA). Supplier does not use Railroad Data for model training, benchmarking, or any purpose other than support.

**Aggregated learning:** Supplier may use anonymized, aggregated data (e.g., "across all deployments, bearing failures typically occur at X temperature range") to improve the Platform, **provided such data cannot be traced back to the Railroad** and does not reveal its competitive position or operational details. See D13 §2.

## 10. Audit rights

### 10.1 Security audit

Once per year, the Railroad may audit Supplier's compliance with this DPA. Audit scope is limited to:
- Supplier's security policy and training records.
- Incident response procedures and logs.
- Subprocessor list (currently none).
- Dependency management for the past 12 months, via **D10** and the release notes. **SBOM auditing becomes available when §7.2's gap closes (target Q1 2027)**; until then the audit is conducted against D10 and the source tree.

Audit is conducted by the Railroad or a third party bound by confidentiality. Supplier provides documentation and, if requested, interviews with security personnel.

### 10.2 SBOM verification

**Effective when an SBOM exists (target Q1 2027).** The Railroad may then independently verify the SBOM against the actual dependencies installed in the Platform. If discrepancies are found, Supplier investigates and remediates within thirty days.

**Until then, the equivalent right is this:** the Railroad may compare D10 against the dependency set actually installed at its site, using `pip freeze` or equivalent on its own host, and raise any discrepancy. Supplier responds within thirty days. **The right exists now; only its artefact changes.** An audit right that begins in 2027 is not an audit right, so it would have been wrong to leave this section with no effect at all.
