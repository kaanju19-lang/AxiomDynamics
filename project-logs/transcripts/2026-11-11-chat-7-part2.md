The design choice:

| Option | Model | Pros | Cons | Best for |
|--------|-------|------|------|----------|
| **A: Reuse accounts table** | Ingest token = reviewer session | Simple: one auth path, one token type | Confusion: a collector is not a reviewer; a revoked reviewer blocks ingests | Convenience, not architecture |
| **B: Separate collector credential** | New `ingest_tokens` table or ephemeral flow | Clear separation: ingest = sensor auth, disposition = human auth | More code: two token paths, two lifetimes | Auditable distinction, matches the domain |

**Decision: Option B (separate collector credential).** Here's why:

1. **Audit clarity**: The docket distinguishes "reviewer" (makes dispositions) from "detector/collector" (sends readings). Reusing the account table blurs that line in code.
2. **Lifecycle mismatch**: A reviewer's session expires in hours; a collector might run for weeks. One table for both is a landmine.
3. **Revocation semantics**: If I revoke a reviewer's cert, should that stop their old sessions from writing dispositions? **Yes.** Should it stop the automated collector from ingesting? **Probably not** — the collector is a machine, not a person who just left.
4. **Future: auditor's question**: "Are these the same credential?" should have an answer that is not "sort of."

**What gets built:**
- `backend/ingest_auth.py`: ephemeral bearer tokens for collectors (issue on enrollment, no TTL, one-use or long-lived at deploy-time config, revocation by enrollment revocation)
- `POST /api/ingest` gates on the same pattern: `Authorization: Bearer`, 503 if no collector enrolled, 401 if token absent/invalid
- Docket update: B01 §7 item 5 clarifies "collector authentication" is now distinct from "reviewer authentication"
- D09 clarifies the same
