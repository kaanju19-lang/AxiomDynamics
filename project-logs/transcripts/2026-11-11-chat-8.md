## What the phase actually produced

The carry-forward listed four surviving mutations as test gaps. Closing them found that description was only three-quarters accurate, and the interesting part is the quarter that was wrong.

M5 and M9 were exactly what they were said to be — no direct route call, and a chain test that tripped the `prev_hash` check while never reaching the `entry_hash` check. M9 and M10 now each fail one distinct test.

M3 needed a case nothing had: a garbage body *plus an unknown token*. The existing test sent garbage with no token, which refuses before any write. M2 was the trap. I first concluded it was an equivalent mutant: an empty token flows into `resolve_token`, which raises for an empty token, so you get the same 401 and the same zero rows either way. The audit falsified that. The status and row count match, but **the error text does not** — the handler names the collector enrollment, the route does not. I had compared the status code and the side effects and called that "identical behaviour", without ever comparing the one thing the caller actually reads. It's now killed by asserting the message, and the drivers' escape hatch I'd built for it is gone.

## Two defects in the driver, found after everything was green

Both were mine, and both were the same shape as the ledger and ROI defects already in this project's history: a mechanism that turns red into green without changing what's under test.

The `EQUIVALENT` table I added was keyed by mutation *index*. The auditor swapped a genuine survivor into that slot and the driver printed "equivalent" and exited 0 — it would have silently absorbed any real survivor landing there. The pycache isolation was worse in a quieter way: the suite runs under `-I`, and `-I` sets `sys.pycache_prefix` to `None`, discarding `PYTHONPYCACHEPREFIX` entirely. The redirect was inert and bytecode still reached the source tree. Both verified empirically rather than reasoned about; the driver now uses `-X pycache_prefix=`, which survives `-I`.
